# 外部API・外部インターフェース

具体的なベンダー選定は行わず、必要な機能要件と選定時の判断基準を定義する。ベンダー確定は要件定義書 未決事項3と連動して別途行う。

## 1. 認証

| 項目 | 内容 |
|------|------|
| 方式 | ソーシャルログイン(Google等) |
| 用途 | ログイン、ユーザー識別、訪問記録の紐付け |
| バックエンドでの検証 | 発行されたIDトークンをバックエンドAPIで検証し、内部のuser_idと紐付ける |

## 2. 距離行列API(L1)

| 項目 | 内容 |
|------|------|
| 用途 | 候補道の駅間の全ペア所要時間・距離を取得(要件定義書 4.2) |
| 必須機能 | 高速道路回避オプション(avoidHighways等) |
| 呼び出しタイミング | バックエンドがL3ソルバの計算前にバッチ取得。モバイルアプリから直接は呼ばない |
| コスト対策 | 候補を事前に地理的な範囲で絞り込んでから行列取得する(要件定義書 4.2の注意点) |
| 選定基準 | 国内カバレッジ、課金体系、レート制限(NFR-3) |

## 3. 地図表示・ルート描画

| 項目 | 内容 |
|------|------|
| 用途 | 確定した周遊ルートを地図上に表示(S4 ルート提案結果画面) |
| 備考 | L1で使う距離行列APIと同一ベンダーの地図SDKを使うと実装コストが下がる可能性が高いが、必須ではない |

## 4. 道の駅データソース

| 項目 | 内容 |
|------|------|
| 用途 | 道の駅マスタ(名称・位置・営業時間・定休日・施設情報)の初期データおよび継続更新 |
| 状態 | **未確定**(要件定義書 未決事項1)。全国「道の駅」連絡会等の情報を機械可読で取得できるか、手入力/クラウドソーシングで補うか検討中 |
| 外部設計上の扱い | データソースが確定するまでは、バックエンドAPIの道の駅マスタ取得口(内部API)は外部データソースの形式に依存しない抽象化されたスキーマ([02_data-model.md](./02_data-model.md))を返す形にしておく |

## 5. バックエンド内部API(モバイルアプリ向け)

MVPで必要になる内部APIエンドポイントの一覧(詳細なリクエスト/レスポンス仕様は実装着手時に詰める)。

| エンドポイント(概念) | 用途 | 対応画面 |
|----------------------|------|---------|
| ログイン検証 | IDトークン検証、ユーザー作成/取得 | S1 |
| 道の駅候補取得 | 条件(エリア等)に応じた候補一覧取得 | S3 |
| 経路最適化 | RouteRequestを受け取りRouteResultを返す(L1〜L3実行) | S2→S4 |
| 道の駅詳細取得 | 施設情報・人気度・トイレ評価取得 | S5 |
| チェックイン登録 | 訪問記録の作成 | S6 |
| 実績取得 | 都道府県別・全国の達成率取得 | S7 |
