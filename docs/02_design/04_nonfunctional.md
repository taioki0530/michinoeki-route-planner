# 非機能設計方針(モバイルアプリ前提)

要件定義書のNFR-1〜6を、モバイルアプリという構成が確定した前提で具体化する。

| ID | 要件定義書での要件 | モバイルアプリでの対応方針 |
|----|---------------------|---------------------------|
| NFR-1 | 経路計算は数秒以内に応答 | 計算はバックエンドで実行し、モバイル側はローディング表示で体感速度を担保する。具体的な目標秒数は未確定([99_open-issues.md](./99_open-issues.md)) |
| NFR-2 | 営業時間・定休日データの鮮度維持 | モバイル側は影響を受けない(バックエンド/データ運用側の課題)。ただしアプリ側は「データ最終更新日」をS5(道の駅詳細)に表示し、鮮度をユーザーに示す |
| NFR-3 | 外部APIの規約・課金・レート制限準拠 | 外部API呼び出しはすべてバックエンド経由に集約し、モバイルアプリから外部APIを直接叩かない(APIキー保護・呼び出し量の一元管理のため) |
| NFR-4 | オフライン/圏外での縮退動作 | 直近に取得した道の駅一覧・詳細情報は端末にキャッシュし、圏外でも閲覧のみ可能とする。新規の経路計算(L1〜L3)はオンライン必須とし、圏外時はその旨を明示する |
| NFR-5 | 対応エリア・データ項目の段階的拡張 | データモデル([02_data-model.md](./02_data-model.md))・内部API([03_external-interfaces.md](./03_external-interfaces.md))はエリアを限定するフィルタ設計とし、対象都道府県を増やしてもスキーマ変更が不要な形にする |
| NFR-6 | 片手・短時間で操作できるUI | 画面数を最小限(S1〜S7)に抑え、S2(条件入力)は入力項目を絞る。詳細なUI設計は各画面実装時に詰める |

## 位置情報・個人情報の取り扱い(追加論点)

要件定義書には明記されていなかったが、モバイルアプリで現在地・訪問履歴という個人情報を扱う以上、以下は実装前に確定させる必要がある。

- 位置情報の利用許諾(アプリ起動時の許可ダイアログ文言、「使用中のみ許可」で足りるか)
- 訪問記録・現在地情報の保存期間、第三者提供の有無(プライバシーポリシーの要否)
- ストアアカウント削除・退会時のデータ削除方針

→ 詳細未確定のため [99_open-issues.md](./99_open-issues.md) に記載。
