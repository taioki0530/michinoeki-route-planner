# 道の駅周遊コンシェルジュ 要件定義書

> 企画背景・目指す姿は別紙「企画書」を参照。本書は機能要件・非機能要件・技術方針を定義する。

## 1. サービスの核となる問題定義

本サービスの核は **制約充足つき経路最適化** である。単なる最短経路(距離最小化)ではなく、営業時間・定休日という時間的制約と、道路条件という経路的制約を満たしながら、訪問できる道の駅の数・質(効用)を最大化する。学術的には **時間枠付きオリエンテーリング問題(Orienteering Problem with Time Windows, OPTW)** に相当する。

| 問題 | 内容 |
|------|------|
| TSP(巡回セールスマン問題) | 全地点を回る最短経路 |
| OP(オリエンテーリング問題) | 予算(時間/距離)内で獲得スコアを最大化する地点集合と経路を選ぶ |
| **本サービス = OPTW** | OP + 時間枠(営業時間)+ 道路種別ペナルティ |

「閉店時間が迫る中で最大限巡る」という課題はOPTWそのものであり、この認識が全機能の骨格を決める。

## 2. 機能要件(Functional Requirements)

### FR-1. 経路最適化ドメイン(中核)

| ID | 要件 |
|----|------|
| FR-1.1 | 現在地・出発時刻・帰着希望時刻(または総所要時間の上限)を入力できる |
| FR-1.2 | 営業時間・定休日・臨時休業を制約とし、時刻に間に合う道の駅のみを候補とする |
| FR-1.3 | 予算(時間/距離)内で訪問数または効用を最大化する周遊順序を算出する |
| FR-1.4 | 道路条件(高速回避)を経路コストに反映できる |
| FR-1.5 | 各道の駅での滞在時間を考慮して到着/出発時刻を計算する |

> **理論的注意(FR-1.3)**: OPTWはNP困難。候補数(数百〜千規模)の全探索は非現実的なため、「候補生成 → メタヒューリスティクス(貪欲法＋局所探索、または遺伝的アルゴリズム)」の二段構えとする。厳密解ではなく「実用上十分に良い解を高速に返す」方針とし、NFR-1(応答時間)と併せて精度を決める。

### FR-2. 情報提供ドメイン

| ID | 要件 |
|----|------|
| FR-2.1 | 各道の駅の施設情報(レストラン・売店とその営業時間)を表示 |
| FR-2.2 | 人気度・トイレの清潔さを表示する(初期は表示のみ。将来的に効用スコアへの重み付けを検討) |
| FR-2.3 | 周辺観光スポットを表示し、経由地としてルートに組み込める |

> **設計上の論点(FR-2.2)**: 人気度・トイレ清潔さは主観データ。「最適化に影響させる」のか「参考表示のみ」なのかを切り分けないと最適化ロジックが複雑化する。初期は表示のみとし、段階的に重み付け導入。

### FR-3. 記録・ゲーミフィケーションドメイン

| ID | 要件 |
|----|------|
| FR-3.1 | 訪問済み道の駅を記録(チェックイン)できる |
| FR-3.2 | 達成率(都道府県別・全国)を表示 |
| FR-3.3 | 訪問回数に応じたバッジ・キャラ等の収集要素を解禁 |

## 3. 非機能要件(Non-Functional Requirements)

| カテゴリ | ID | 要件 | 論点 |
|---------|----|----|------|
| 性能 | NFR-1 | 経路計算は候補数◯件で数秒以内に応答 | OPTWは重い。目標応答時間を先に決め、許容する最適化精度を逆算する(精度と速度のトレードオフ) |
| 正確性 | NFR-2 | 営業時間・定休日データの鮮度を保つ更新手段を持つ | 制約データが古いと「着いたら閉まってる」課題が再発。データが本質的価値であり最重要 |
| データ源信頼性 | NFR-3 | 外部API(経路・地図)の利用規約・課金・レート制限に準拠 | 経路計算を外部APIに依存する場合、コスト構造がサービス成立性を左右する |
| 可用性 | NFR-4 | オフライン/圏外(山間部)での縮退動作 | 対象が電波の弱い山道。移動中に使えないと本末転倒 |
| 拡張性 | NFR-5 | 対応エリア・データ項目を段階的に追加できる構造 | まず一地方で検証し全国展開する想定 |
| ユーザビリティ | NFR-6 | 運転前提のため、片手・短時間で入力/確認できるUI | 運転中の操作は安全性に直結 |

## 4. 技術方針

### 4.1 問題の3レイヤー分解

FR-1は性質の異なる3層が重なる。層ごとに「外部API/自前実装」の判断が変わる。

| レイヤー | 問題の性質 | 外部APIで解けるか | 判定 |
|---------|-----------|-----------------|------|
| L1. 2点間の距離・時間 | 最短路探索(Dijkstra/A*) | ○ 完全に解ける | **外部API一択** |
| L2. 巡回順序の最適化 | TSP | △ waypoint最適化で可(時間枠は無視) | **外部API＋補正** |
| L3. 訪問対象の選択＋時間枠 | OPTW(効用最大化) | ✕ 汎用APIは解かない | **自前実装が必須** |

> **要点**: L1・L2は枯れた問題で、道路ネットワークデータの整備・維持コストが莫大なため自前実装は非合理。自前実装の独自価値が出るのはL3のみ。本サービスの独自価値はL3にあり、開発リソースをここに集中する。

### 4.2 推奨アーキテクチャ

```
[自前]    L3: OPTWソルバ(訪問対象選択 + 時間枠制約 + 効用最大化)
              ↑ 距離・時間行列を要求
[外部API] L2: waypoint順序最適化、または自前で行列を組んでソルバに渡す
[外部API] L1: 距離行列API(Distance Matrix)で全ペア所要時間を取得
[外部API] 描画: 確定ルートのpolylineを地図表示
```

> **勘所**: L3ソルバが必要とするのは「道の駅間の所要時間行列」。これを外部APIから一度バッチ取得すれば、効用最大化計算は自前・オフラインで完結できる。API呼び出しを行列取得の1回に集約でき、コスト(NFR-3)と速度(NFR-1)の両方に効く。距離行列APIはN地点でN²ペア課金となるため、候補を事前に地理的に絞ってから行列を取る設計が必須。

### 4.3 道路条件の対応方針(決定事項)

- **高速回避**: 外部APIの標準機能(avoidHighways等)で対応 → MVPで提供。
- **山道回避**: 主要な経路APIに標準機能が存在しない。**MVPでは見送り**とする。将来的には、複数候補ルートを取得し各ルートの標高プロファイル(獲得標高)で事後フィルタする方式を検討する。

## 6. 未決事項(次に詰めるべき論点)

1. **データ調達・維持の方針(NFR-2)** — 価値の源泉。正確な営業時間・定休日・施設・トイレ情報を、機械可読取得/手入力/ユーザー投稿(クラウドソーシング)のどれで確保・維持するか。事業の生命線。
2. **L3ソルバの具体アルゴリズム設計** — OPTWをどのメタヒューリスティクスで解くか。
3. **距離行列APIのコスト試算とベンダー比較** — 課金体系・国内カバレッジで具体ベンダーを選定。
4. **NFR-1の目標応答時間の確定** — これが最適化精度の許容範囲を規定する。
